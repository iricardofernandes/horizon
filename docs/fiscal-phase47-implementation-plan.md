# Phase 47 — National NFS-e and municipal capability

Status: **delivered for simulation on 2026-09-26**
([evidence](fiscal-phase47-evidence.md)). This is the execution record for [Phase 47 in the fiscal roadmap](fiscal-implementation-plan.md#47--national-nfs-e-and-municipal-capability).
The environment is still simulation-only. Every NFS-e in this phase is generated by a
deterministic simulator of the Sefin Nacional (national NFS-e issuing system). Nothing
contacts an authority, and Fiscal never publishes a stock, receivable or payable
effect.

## Result

Horizon can issue a **national NFS-e** for a reviewed service, as its own capability:
- a **service fiscal profile**, distinct from the goods classification: national tax
  code (`cTribNac`, LC 116 item, subitem and national split), NBS code and ISSQN
  treatment, revisioned and effective-dated, checked against the pinned national lists;
- a **service origin** with its own **competence date**, frozen and encrypted, that a
  person reviews now and that Phase K contract periods will reach through the same
  idempotent source key;
- a **versioned municipal registry** that says, per municipality, whether the national
  system issues its NFS-e (convênio, national environment, national public issuer and
  start date), imported from the official adhesion list with row locators;
- a capability keyed by **municipality** (not UF), resolved from the issuer's registered
  address and the registry;
- its own **DPS** (Declaração de Prestação de Serviço) builder, identifier, numbering,
  signature and XSD validation (layout 1.01);
- its own simulated authority: synchronous generation of the NFS-e (with the 50-digit
  access key), consultation by DPS identifier and by access key, and events;
- **cancellation** (event 101101) inside the municipality's window and **substitution**
  (a new DPS with `subst`, which cancels the original with event 105102).

Models 55 and 65 keep their code paths, events and tests unchanged.

## Starting point

- `fiscal_documents.model`, the numbering tables, capabilities, rules and the calculation
  input already accept `nfse`; capabilities already accept jurisdiction kind
  `municipality` for it. No rule, fixture or capability row exists.
- The calculation engine already supports service lines (`serviceId`,
  `classifications.service`) and rules selected by `competence_date`.
- Catalog items can be `service`, but Catalog classifies goods only (NCM). There is no
  service fiscal profile anywhere.
- Every origin today is a sale (Sales intent), a reviewed manual sale or a linked
  document. None can carry a service or a competence date.
- The issuance binding requires a 44-character NF-e access key; an NFS-e key only exists
  after the authority generates it.

## Decisions frozen by this plan

1. **The NFS-e is a document of model `nfse` in the same lifecycle.** It reuses the
   document states, number reservations, the calculation lock, the durable dispatch
   queue, the outbox and the artifact store. Everything model-specific is new code under
   `fiscal/src/nfse/`: service profiles, municipal registry, service origins, readiness,
   DPS builder, signature, schema validation, events, simulator, issuance, cancellation,
   substitution and routes.
2. **A service fiscal profile is Fiscal reference data.** `fiscal_service_profiles` holds
   one revision per Catalog service item: `nationalTaxCode` (6 digits), `nbsCode`
   (9 digits), optional municipal code, ISSQN treatment (only `1`, taxable, is
   supported), description and effective date. A revision is created by a reviewer, is
   immutable and must exist in the pinned national lists. The Catalog item must be an
   active `service`.
3. **A service origin freezes what was provided.** `POST /fiscal/service-origins` takes the
   establishment, issuer and recipient (tomador) revisions, the service item and profile
   revision, the **competence date**, the amount, a description and a reason. It stores an
   encrypted payload with its digest. An optional `sourceKey` (module, document type, id,
   period) is unique per tenant: two requests with the same key and facts return the same
   origin even with different idempotency keys, and differing facts are refused. Phase K
   will send contract periods through that key. The competence date is on or before the
   issue date and inside the reviewed rule window.
4. **The municipality decides, through a versioned registry.**
   `fiscal_nfse_registry_versions` holds a reviewed import of the official adhesion list
   (digest, publication date, reviewer). `fiscal_nfse_registry_entries` holds, per
   municipality: IBGE code, UF, name, convênio status, national-environment adhesion,
   national-public-issuer adhesion, start date and the row locator in the source. The
   national route is **supported** only when the convênio is active, the municipality
   adheres to the national public issuer (rule E0039) and the competence date is on or
   after the start date (E0016). A municipality with its own issuing system (for example
   Campinas: convênio active, national issuer "Não") is **unsupported**. It needs its own
   adapter and support row. A statistic or a municipality absent from the reviewed version
   is never support.
5. **The capability is per municipality.** A row has model `nfse`, jurisdiction kind
   `municipality`, the IBGE code, operation `service-provision`, adapter
   `nfse-national-simulator-v1` and fixture `rtc-v0057-nfse-service-provision-2026-01`.
   Readiness requires:
   - the issuer's registered municipality to be the capability's municipality and a
     supported registry entry;
   - an active service profile revision at the competence date;
   - the recipient to have a CPF or CNPJ and a national address.
   A refusal answers `MUNICIPALITY_UNSUPPORTED`, `SERVICE_PROFILE_MISSING` or
   `CAPABILITY_UNSUPPORTED`. The issuance and the worker check the registry again, so an
   unsupported municipality never reaches the transmission boundary.
6. **Taxes come from a reviewed service fixture.** The calculation line is the service,
   with `classifications.service` = `cTribNac` and rules selected by the competence date:
   - `ISS` (legacy group) at the rate the municipal parameter gives for the service;
   - `CBS`, `IBS_UF` and `IBS_MUN` at the RTC V0057 2026 reference rates.

   The municipal rate is not pinned (see Sources). The local rollout sets **2%** as the
   owner's provisional simulation reading, and the simulator applies the same parameter
   independently. Per rule E0617, a non-Simples issuer in an active municipality **does
   not** send `pAliq`: the authority applies its parameter. The generated NFS-e values are
   reconciled with the locked calculation, and a difference is recorded as
   `CALCULATION_MISMATCH` evidence.
7. **The DPS is built by its own code.** `infDPS` layout 1.01:
   - `tpAmb` 2 in simulation, `dhEmi` at signing in the issuer's timezone, `verAplic`;
   - `serie` (the document series, 1–49999: the range for the taxpayer's own
     application, E0010) and `nDPS` (the reserved number);
   - `dCompet`, `tpEmit` 1 (provider), `cLocEmi` (issuer municipality);
   - `prest` (CNPJ, `regTrib` with `opSimpNac` 1 and `regEspTrib` 0 for a Lucro
     Real/Presumido issuer);
   - `toma` (CPF or CNPJ, name, national address);
   - `serv` (`locPrest`/`cLocPrestacao` = issuer municipality, `cTribNac`, `xDescServ`,
     `cNBS`);
   - `valores` (`vServ`, `tribMun` with `tribISSQN` 1 and `tpRetISSQN` 1, `totTrib` with
     `indTotTrib` 0);
   - `IBSCBS`: `finNFSe` 0, `cIndOp` 100301 (other onerous services, acquirer's domicile,
     Anexo C), `indDest` 0 and `gIBSCBS` with CST 000 and `cClassTrib` 000001.

   The identifier is `DPS` + `cLocEmi` + `2` (CNPJ) + CNPJ + series (5) + number (15)
   (E0004), and it is bound before sending. The DPS is signed on `infDPS` (enveloped,
   C14N) and validated against the pinned `DPS_v1.01.xsd`.
8. **A lost response is reconciled by DPS identifier before any resend.** The simulated
   authority is synchronous, like the Sefin Nacional:
   - a timeout leaves the document `unknown`;
   - the worker then asks `GET /dps/{id}` and, when an NFS-e exists, reads it by key and
     records it;
   - only a DPS the authority never received is sent again;
   - a naive resend of a DPS that was already generated is rejected with E0014, which the
     simulator enforces and a test exercises.
9. **The simulator is the national system's shape.** `DeterministicNfseSimulator`
   validates what the pinned rules make checkable locally:
   - the DPS identifier (E0004), the environment (E0006), `dhEmi` (E0008), the series
     range (E0010), duplicates (E0014) and competence (E0015/E0016);
   - its own registry of convênios (E0037–E0039);
   - the absence of `pAliq` for a non-Simples issuer (E0617).

   It generates an NFS-e XML (`NFSe` 1.01 with `infNFSe`, `cStat` 100, `nNFSe`, the
   applied rate and `vISSQN`, and the DPS inside), signed by a simulation credential and
   valid against `NFSe_v1.01.xsd`. It keys the NFS-e by a 50-digit access key: municipality,
   environment 2, inscription type, CNPJ, number, year-month, a code and a check digit
   (modulo 11, the simulator's own choice: the annex does not define the check digit).
10. **Cancellation is event 101101 inside the municipal window.** A reviewer gives a reason
    code (1 emission error, 2 service not provided, 9 other) and a text of 15–255
    characters. Fiscal signs a `pedRegEvento` (`PRE` + key + `101101`), validates it
    against `pedRegEvento_v1.01.xsd` and queues it. It is refused after the window of the
    reviewed profile (`CANCELLATION_WINDOW_ELAPSED`, E0822), counted from the NFS-e
    `dhProc`. The local rollout sets 30 days as the owner's provisional reading. A refused
    cancellation keeps the NFS-e authorized.
11. **Substitution is a new DPS that cancels the original.**
    `POST /fiscal/service-documents/{id}/substitutions` takes a reason code (01–05, 99), an
    optional text (required for 99, E0078) and a corrected service origin. The substitute:
    - keeps the recipient, competence, service code and place of provision of the
      original, since a non-Simples issuer may not change them (E0058/E0060); only the
      value and description may change;
    - is a new document linked by `substitutes_document_id`, with its own number;
    - carries `subst` (`chSubstda`, `cMotivo`, `xMotivo`).

    When the authority generates it, it records event 105102 on the original, which moves
    from `authorized` to `cancelled` in the same transaction. A rejected substitute leaves
    the original authorized. An original cannot be substituted twice, cancelled while a
    substitution is pending, or substituted after its window.
12. **Service outcomes have their own event.** `fiscal.service-document.simulation-outcome`
    v1 carries:
    - the outcome (`authorized`, `rejected`, `cancelled`), the document, root and
      revision;
    - the service origin and its source key when present;
    - the municipality, the competence month, and `substitutedBy` for a cancellation by
      substitution;
    - the adapter version and status digest.

    It carries no access key, recipient identity or XML, and names no stock or money
    owner: NFS-e issuance posts nothing. The model 55 and 65 events stay unchanged.
13. **The issuance profile carries the reviewed NFS-e facts.** A `service` block:
    `capabilityId`, `cancellationWindowDays`, `substitutionWindowDays`, `operationIndicator`
    (`cIndOp`) and `ibsCbs` (`cst`, `classification`). The simulator receives the
    municipal parameters (ISS rate per `cTribNac`, deadlines) of the reviewed scenario.

## Changes made during implementation

- **XSD defect.** In the pinned 1.01 package, `TSSerieDPS` is `^0{0,4}\d{1,5}$`. XSD
  regular expressions have no anchors, so a conformant validator rejects every real
  series. Horizon validates with the two literal characters removed, only after the
  package digest matched, and a test fails if the published pattern differs.
- **ISS per municipality.** The rule scope has no municipality, so each municipality has
  its own calculation operation, `rtc-v0057-nfse-service-<IBGE>`. The ISS rule sits in
  its own package, the owner's provisional reading of the municipal parameter. The
  service reference entry is national (`BR`), like the national service list.
- **The provider in the NFS-e.** A provider-issued DPS must not carry the provider's name
  or address (E0121, E0128). The simulated system takes them from the issuer projection
  and the profile's `issuerAddress`, standing for the CNPJ cadastre.
- **Artifacts and reads.**
  - The generated NFS-e is kept as `nfse_xml`, and its digest is the observation's
    protocol digest.
  - Event 105102 is kept on the substitute as `substitution_event`.
  - `/documents/{id}/v2` and `/documents/{id}/artifacts/v2` answer 404 for an NFS-e
    because their NF-e schemas cannot describe it. The v1 artifact list,
    `/service-documents/{id}` and the calculation routes read it.
- **Service origins** keep their municipality in a column, for reads and events. The
  substitute's reason lives in `fiscal_nfse_substitution_requests`.
- **Simulator choices:**
  - the access-key check digit is modulo 11, since Anexo I does not define one;
  - signatures use RSA-SHA256, since the algorithm is not pinned;
  - the NFS-e number equals the DPS number;
  - the system answers in UTC−03:00.
- **Event order.** The substitute's authorization and the original's cancellation share
  one transaction and one `created_at`, so readers must not rely on their relative
  order.

## Exit evidence (from the roadmap)

- One national NFS-e tuple (simulation, one establishment, São Paulo 3550308,
  `service-provision`) passes issue, query and the supported correction and cancellation
  flows: substitution and event 101101.
- An unsupported municipality cannot reach the transmission boundary: readiness,
  issuance and the worker refuse it, and the simulator is never called.
- A lost response is reconciled by DPS identifier before any retry, and only one NFS-e
  exists.
- Duplicate source keys map to one fiscal origin (the Phase K contract-period path).
- Service tax (ISS) and IBS/CBS source versions appear in the calculation explanation.
- The model 55 and 65 tests stay unchanged and green.

**Restricted production (the roadmap's homologation) stays the activation gate.** It
needs an establishment A1 certificate, the Swagger contract and municipal parameters
(retrievable only with that certificate) and a Fiscal review. The owner's standing
instruction is simulation only, as in Phases 43–46.

## Non-goals

- Restricted-production or production transmission, and the DANFSe PDF: in the
  national system, the ADN generates it (`/danfse`).
- Municipal (non-national) issuing systems, NFS-e via, tomador/intermediary issuance,
  Simples Nacional and MEI issuers, withholding (`tpRetISSQN` 2/3), deductions,
  benefits, exports, construction and events of other categories (manifestations,
  fiscal analysis).
- Service orders and recurring contracts (Phase K), which will call the service-origin
  source key.
- Operator screens (Phase 48).
